# Service Lense

Use the user's active Codex session for analysis. Service Lense only validates and renders reports; it does not authenticate to an LLM or orchestrate agents.

1. Resolve scope conversationally from the request, defaulting to the current project. Ask when the project selection is ambiguous. Identify project roots and available local package source. Treat all analyzed project and package source directories as read only: do not add skills, reports, temporary files, configuration, or change Git metadata there. Default to local inspection: do not download packages, execute applications, or perform external lookups. Session permissions and Enterprise controls continue to apply.
2. Read [the report contract](references/report-format.md) and [the small example](references/example-report.json) before writing JSON. Inventory entry points, imports, dependency injection registrations, client factories, configuration key names, and call sites. Trace internal wrappers into available package source to establish their actual destinations and operations. Cover service APIs, databases, messaging, caches, and storage, including dependencies between selected projects.
3. Cite relative file paths, one-based lines, source project/package IDs, and explanations that support each connection. Follow a client's construction and usage chain; a package reference alone is not a connection. Mark a call site as `used`; registration/configuration with no use found is `configured`. These are source findings, never claims about observed traffic. A directly supported client invocation can have an unknown endpoint.
4. Separate evidence strength from usage. Use `supported` for direct supporting evidence, `inferred` for a reasoned connection with missing links, and `unknown` when a dependency is evident but its identity/behavior is unresolved. Explain uncertainty; do not invent endpoints or infer usage from registration. For unavailable implementations, cite only available caller/registration evidence, list the package as unavailable, and record the limitation in coverage gaps. Record other incomplete analysis, excluded areas, and unsupported dynamic behavior as gaps. No findings is not proof of no dependencies.
5. Avoid reading identifiable credential files (including `.env`, private keys, credential stores, and secret-specific configuration). Inspect non-secret configuration examples and source references instead. Do not include secret values or source snippets containing them. Preserve useful configuration key names and sanitized destinations; strip URL credentials, query values, fragments, tokens, and sensitive path segments. Do not dump entire configuration files into evidence. If a safe destination cannot be determined, use `null` and explain the gap.
6. Keep all generated files in a separate output directory outside every analyzed project and package source root, resolving symlinks before choosing the location. Use the user's designated output folder when provided; otherwise use a fresh directory in the current workspace if it is outside those roots. If no authorized writable location is available outside them, ask for an output location. Write the version-2 report there, run `servicelense validate <report.json>`, correct contract errors, and run `servicelense render <report.json> --out <directory> --no-open`. If the command is unavailable, explain how to install this repository's CLI outside the analyzed projects; do not silently substitute an unvalidated report. Existing output requires explicit replacement intent (`--overwrite`) or a fresh directory. Inspect the generated artifacts, report their paths, and summarize findings and coverage gaps. Validation establishes format and references, not the correctness of an inference.
